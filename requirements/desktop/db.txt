DATABASE GOAL

Sync needs a serious, reliable, local-first data system.

The database should allow Sync to:
1. Remember projects.
2. Store AI conversations.
3. Store messages and model metadata.
4. Store task graphs.
5. Store ignored, skipped, completed, failed, and blocked tasks.
6. Store file changes and diffs.
7. Store file snapshots for rollback.
8. Store AI tool calls.
9. Store Git and GitHub actions.
10. Store MCP servers and MCP tool calls.
11. Store connectors and connector usage history.
12. Store agent runs, agent handoffs, and agent logs.
13. Store project memory.
14. Store prompt templates.
15. Store settings.
16. Store permissions.
17. Store model/provider configuration.
18. Store logs and diagnostics.
19. Support export/import.
20. Support backup and restore.
21. Protect sensitive data.
22. Work fast even after many sessions.


DATABASE STRATEGY

Use SQLite as the default local database.

SQLite should be the main local datastore because Sync is a desktop app and must work offline, locally, quickly, and without requiring a server.

SQLite should store:
- projects
- sessions
- messages
- tasks
- task graph dependencies
- agents
- agent runs
- tool calls
- history
- file changes
- diffs
- snapshots metadata
- Git actions
- GitHub actions
- MCP servers
- MCP calls
- connectors
- connector calls
- prompt templates
- project memory
- settings metadata
- permissions
- logs
- diagnostics
- model usage
- audit events

PostgreSQL should be optional and future-oriented.

PostgreSQL may be used later for:
- cloud sync
- team accounts
- multi-device sync
- collaborative projects
- shared prompts
- organization-level history
- remote analytics
- hosted workspace memory
- shared agent configurations
- enterprise deployment

Do not require PostgreSQL for the MVP.

JSON, TOML, and YAML should be used for local config and portable settings, not as the main relational data system.

Use JSON for:
- app settings export
- prompt template export/import
- connector configuration export/import
- model profile export/import
- session export
- tool log export
- project metadata export
- structured agent configuration

Use TOML for:
- stable local app configuration
- advanced developer configuration
- Rust/Tauri-style native configuration
- low-level app preferences

Use YAML for:
- readable workflow definitions
- agent workflow presets
- MCP server presets
- prompt packs
- automation recipes
- user-editable configuration templates

Important rule:
SQLite is the source of truth for runtime app data.
JSON/TOML/YAML are config/export formats.
PostgreSQL is optional for future sync/cloud mode.

DATA MODEL PRINCIPLES

The database should be designed around traceability.

Every important action should be connected to:
- project
- session
- message
- agent
- task
- tool call
- file change
- approval decision
- history event
- timestamp

The user should be able to answer:
- What did the AI do?
- Why did it do it?
- Which agent did it?
- Which task caused it?
- Which tool was used?
- Which files changed?
- Who approved it?
- What was the result?
- Can it be reverted?
- Was it connected to GitHub, MCP, or a connector?
- Was it risky?
- Was it blocked or ignored?

Use stable IDs for every important object.

Each table should include:
- id
- created_at
- updated_at
- deleted_at if soft delete is useful
- project_id if project-specific
- session_id if session-specific
- status if lifecycle-based
- metadata_json for flexible future data when needed

Use soft delete for important user data:
- projects
- sessions
- tasks
- prompts
- memory records
- snapshots
- connectors

Do not soft delete tool logs or audit logs unless the user explicitly clears history.

SENSITIVE DATA AND SECURITY

Sensitive data rules:
1. Do not store API keys in plain text.
2. Do not store secrets in AI messages.
3. Do not store full secrets in logs.
4. Do not store full secrets in tool outputs.
5. Mask secret-like values before saving logs.
6. Store only metadata for detected secrets.
7. Sensitive file reads require permission.
8. Sensitive file content should not be used as normal AI context.
9. Exported data should mask secrets.
10. Debug bundles should exclude secrets.

API keys:
- Store using a secure local credential mechanism or encrypted storage.
- Database stores only provider metadata, not raw keys.
- Show masked key preview only.
- User can remove or rotate keys.

Secret masking:
Examples:
- sk-1234567890abcdef should become sk-****cdef
- database URLs should hide username/password
- tokens should show only first and last few characters
