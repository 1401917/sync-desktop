You are defining the AI tool system for a desktop AI coding workspace named Sync.

This is NOT a coding task.
Do not write code.
Do not choose frameworks.
Do not generate implementation files.
Do not design UI styling.
Do not focus on colors or visual layout.

Focus only on:

Product name:
Sync

Product type:
Sync is a desktop AI coding workspace for Windows. It allows an AI assistant to help the user plan, build, edit, debug, refactor, review, and manage software projects. The AI should have access to strong tools, but every sensitive action must be visible, controlled, logged, and permission-based.

Main objective:
Create a complete AI tools specification for Sync. The AI should be powerful enough to operate like a professional coding agent, but safe enough that it never secretly modifies files, runs dangerous commands, pushes code, exposes secrets, or performs external actions without the correct permission.

The AI tool system should feel like a controlled operating layer between the AI and the user’s computer, GitHub, projects, files, commands, connectors, and MCP servers.


CORE TOOL PRINCIPLES

1. The AI must be powerful but controlled.
2. The AI can inspect project context after the user opens a project.
3. The AI can propose actions before executing them.
4. The AI must request approval for risky or external actions.
5. The AI must show exactly what it wants to do.
6. The AI must explain why each tool is needed.
7. The AI must show target files, commands, repositories, connectors, or MCP tools before using them.
8. The AI must log every tool call.
9. The AI must never silently access secrets.
10. The AI must never silently delete files.
11. The AI must never silently run commands.
12. The AI must never silently push to GitHub.
13. The user can pause, deny, ignore, or modify tool actions.
14. The user can set tool permission levels globally, per project, per session, or per action.


TOOL PERMISSION LEVELS

Every tool should support permission levels.

Permission levels:
- Disabled
- Ask every time
- Allow once
- Allow for this session
- Allow for this project
- Always allow

Default permission model:
- Reading files inside opened project: Allow for project
- Searching files inside opened project: Allow for project
- Writing files: Ask every time
- Creating files: Ask every time
- Deleting files: Ask every time
- Moving or renaming files: Ask every time
- Reading sensitive files: Ask every time
- Running terminal commands: Ask every time
- Installing packages: Ask every time
- Git status/log/diff: Allow for project
- Git add/commit/push: Ask every time
- Creating GitHub repository: Ask every time
- Creating GitHub issues: Ask every time
- Creating pull requests: Ask every time
- Reading GitHub repository metadata: Ask every time unless connected and allowed
- Using connectors: Ask every time by default
- Using MCP tools: Ask every time by default
- Network requests: Ask every time unless provider is explicitly configured
- Reading API keys: Disabled for AI context
- Modifying app settings: Ask every time
- Modifying permissions: Ask every time


TOOL RISK LEVELS

Each tool call should be classified.

Risk levels:
1. Safe
2. Low
3. Medium
4. High
5. Critical

Safe examples:
- list project files
- read non-sensitive project files
- search project files
- inspect package metadata
- view Git status
- summarize project structure

Low examples:
- create a draft task list
- create a proposed file change
- generate README draft
- inspect repository metadata
- check local dependency list

Medium examples:
- create a new file
- edit a file after approval
- run npm install
- run build command
- create GitHub issue
- create branch
- stage files

High examples:
- delete file
- rename/move multiple files
- modify .env
- commit changes
- push to GitHub
- create public repository
- run unknown shell command
- use external connector with write access

Critical examples:
- delete project folder
- force push
- delete GitHub repository
- make private repository public
- expose secrets
- run destructive system command
- execute downloaded script
- modify Windows security settings

Critical actions should require explicit typed confirmation, not just a normal approval click.

TOOL EXECUTION FLOW

When the AI wants to use a tool, Sync should follow this flow:

1. AI identifies needed tool.
2. AI explains why the tool is needed.
3. Sync checks permission rules.
4. Sync classifies risk level.
5. If approval is required, show approval card.
6. User approves, denies, modifies, or ignores.
7. If approved, Sync runs the tool.
8. Tool result is shown to the user.
9. Result is attached to the session if relevant.
10. Tool call is logged in history.
11. Related task status is updated.

For multi-step workflows:
- AI should create a task list first.
- Each task can require tools.
- Each tool call links to a task.
- User can pause the workflow.
- User can ignore tasks.
- Ignored tasks are skipped.
- Failed tasks show reason.
- Blocked tasks show required permission/context.


APPROVAL MODES

Sync should allow these approval modes:

Manual Mode:
- Every tool action requires approval.

Balanced Mode:
- Safe read-only actions inside project are automatic.
- Writes, commands, GitHub, MCP, and connectors require approval.

Project Trusted Mode:
- Read and low-risk project actions allowed.
- Medium/high/critical actions still require approval.

Autonomous Mode:
- AI can run more actions automatically within configured limits.
- Critical actions still require approval.
- This mode must show a warning before enabling.

Default mode:
